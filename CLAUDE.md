## Architecture invariants

These constrain nearly every implementation decision:

**LLMs provide intelligence, never authority.** Authority, truth, state, and rules live outside the model
(`TechnicalArchitecture.md` §45). Concretely:
- Opportunity Score and Suppression scores are computed **in code**, not generated by an LLM. The LLM may
  explain a score but must not decide it (§16, §17).
- LLMs never touch the DB or external services directly. Every mutation goes
  `LLM → typed tool → Policy Engine → transaction → audit log` (§28).

**Agent isolation against prompt injection.** All external sources are UNTRUSTED (§6). The pipeline is
`untrusted input → Extraction Agent (NO action tools) → structured output → validation → Knowledge →
Planning Agent → Action Agent → Policy Engine → Tools` (§7). Never pass raw external input to an agent that
holds action tools.

**One canonical owner per field.** WordPress remains the Source of Truth in Phase 1; sync is one-directional
(WordPress → CMS as AI). Bidirectional sync is explicitly rejected (§23, §24). Before writing to a
WordPress field, check the field ownership table.

**Knowledge is provenanced, versioned, and temporal.** Facts carry `valid_from` / `valid_until` /
`last_verified_at` / `risk_level`; updates create `knowledge_versions` rather than overwriting, and old
evidence is retained (`DatabaseSchema.md` §11, §12, §20). A fact cannot become published truth without
provenance (§65).

**Actions are gated and reversible.** Every action passes Operational → Editorial → Aggregate policy,
yielding `ALLOW | REVIEW | DENY | FREEZE`. Autonomy is per `(site_id, capability)` on Levels 0–4, and
aggregate limits (pages changed per day, site change ratio, redirect batch size) apply on top of individual
approval. Emergency Stop freezes action tools entirely. Actions group into campaigns to enable rollback.

**Multi-tenancy by `site_id`.** Every major table carries it; cross-tenant knowledge leakage is a
correctness bug, not a nicety.

## Domain vocabulary

The decision enum is closed (`README.md` §18) — proposals resolve to one of:
`KEEP | VERIFY | UPDATE | MERGE | PRUNE | NOINDEX | REDIRECT | RESTRUCTURE | LINK | CREATE | DO NOTHING`.
`CREATE` is deliberately *not* the success case; suppressing unnecessary generation is a first-class outcome.

Two graphs are kept separate and must not be merged: the **Knowledge Graph** (meaning of the world:
entities, facts, relationships) and the **Content Graph** (placement on the web: pages, passages, internal
links, canonical/redirect relations) — `TechnicalArchitecture.md` §15.

Knowledge is hybrid: `Entity`/`Fact`/`Relationship` are structured; `Evidence`/`Observation`/`Question`/
`Problem`/`Experience`/`Claim` stay unstructured. Structure high-harm data first (prices, hours, addresses).

## Implementation ordering

`DatabaseSchema.md` §71–73 defines the build order. Phase 1 minimum tables are listed explicitly (sites,
sources, source_items, evidence, entities, entity_aliases, facts, claims, evidence_links,
knowledge_versions, content_items, content_versions, content_claims, queries, rankings, fact_staleness,
verification_requests, verification_events, opportunities, suppressions, plans, actions, action_results,
review_tasks, policies, site_policies, memories). Do not build Phase 1.5 or Later-Phase tables
(passages, serp_snapshots, campaigns, experiments, …) unless asked.

Work is background-first, not realtime (§38): nightly knowledge refresh, daily GSC import, weekly decay
analysis, hourly verification-response processing.

Model routing (§39): small model for classification/extraction, mid for entity resolution/summarization,
strong for planning and drafting.
