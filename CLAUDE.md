## Repository state

Design-stage repository — **no application code, build system, or tests exist yet**. It currently contains
only the specification set (all at Version 1.0):

- `README.md` — product requirements for Phase 1 (AI Media Operator)
- `docs/TechnicalArchitecture.md` — system components, agent isolation, policy/tool runtime, deployment shape
- `docs/DatabaseSchema.md` — 62 table definitions (§3–§64), indexes, pgvector/JSONB usage, phased rollout

These three documents are the source of truth. When implementing anything, read the relevant section
first — table names, column names, engine names, and decision enums are already fixed there.

Planned Phase 1 stack (`TechnicalArchitecture.md` §47): Rails, PostgreSQL, Solid Queue, optional pgvector,
LLM APIs, Docker, and the WordPress REST / Search Console / GA4 / Slack APIs. Application shape is a
**modular monolith** (§48), not microservices — keep bounded contexts (Ingestion, Knowledge, Search
Intelligence, Content, Automation, Policy, Evaluation) separated inside one app.

Docs are written in Japanese; match that language when editing them.

## Architecture invariants

These constrain nearly every implementation decision:

**LLMs provide intelligence, never authority.** Truth, policy, state, and permissions live outside the model
(`TechnicalArchitecture.md` §1, §51). Concretely:
- Opportunity Score and Suppression scores are computed **in code**, not generated by an LLM. The LLM may
  explain a score or extract features but must not decide it (§15, §16).
- LLMs never touch the DB or external services directly. Every mutation goes
  `LLM → typed tool → Policy Engine → transaction → audit log` (§27).

**Agent isolation against prompt injection.** All external sources are UNTRUSTED (§6). The pipeline is
`untrusted input → Extraction Agent (NO action tools) → structured output → validation → Knowledge →
Planning Agent → Action Agent → Policy Engine → Tools` (§7). The Action Agent never reads raw external
evidence directly.

**Extraction alone does not create truth.** `Source → Raw Item → Evidence/Signal → Candidate Knowledge →
Validation → Knowledge` (`README.md` §10). An LLM extraction is a *candidate*; promotion to Fact requires
validation.

**One canonical owner per field.** WordPress remains the Source of Truth in Phase 1; sync is one-directional
(WordPress → CMS as AI). Unbounded bidirectional sync is explicitly rejected (§22, §23). Before writing to a
WordPress field, check the field ownership table.

**Knowledge is provenanced, versioned, and temporal.** Facts carry `valid_from` / `valid_until` /
`last_verified_at` / `confidence` / `risk_level`; updates create `knowledge_versions` rather than
overwriting, and old evidence is retained (`TechnicalArchitecture.md` §11; `DatabaseSchema.md` §20). A fact
cannot become published truth without provenance (`DatabaseSchema.md` §66).

**Actions are gated and reversible.** Every action passes Operational → Editorial → Aggregate policy,
yielding `ALLOW | REVIEW | DENY | FREEZE` (§26). Autonomy is per `(site_id, capability)` on Levels 0–4 (§30),
and aggregate limits (pages changed per day, site change ratio, redirect batch size) apply on top of
individual approval (§31). Emergency Stop rejects action tools entirely; actions group into campaigns to
enable campaign-level rollback (§32).

**Goals can be refused.** The Feasibility Engine evaluates a goal against search demand, reachable ranking,
expected CTR/conversion, and time horizon, and may reject it or return a corrected version — "目標を突き返
せるAI" is a stated design principle (`README.md` §28). Never hand a goal straight to an autonomous loop.

**Multi-tenancy by `site_id`.** Every major table carries it; cross-tenant knowledge leakage is a
correctness bug, not a nicety.

## Deployment constraints

`PaaS-first, Docker-portable` is an architecture-level requirement, not an ops detail — it constrains what
the application may depend on:

- **PostgreSQL is the only mandatory stateful component** (§41, `DatabaseSchema.md` §75). Redis,
  Elasticsearch, Neo4j, Kafka, a dedicated vector DB, persistent disk, and Kubernetes must NOT become
  required. Use Solid Queue (Postgres-backed) rather than a Redis-backed queue (§42); pgvector is optional
  (§37).
- **One image, multiple processes** — web, worker, and scheduler run the same Docker image with different
  commands (§44). Keep PaaS-specific code out of the application.
- **Do not trust the local filesystem** for persistence (§43). Phase 1 media stays in the existing WordPress
  media library; object storage is a later, optional addition.
- **Boot on a minimal env** — `DATABASE_URL`, `LLM_API_KEY`, `APP_SECRET` should be enough to start (§45);
  WordPress / GSC / GA4 / Slack are connected from the UI, not required env.
- **Secrets are never stored in plaintext in the DB** — `connector_credentials` holds a
  `secret_reference` to a secret manager (`DatabaseSchema.md` §64).
- Setup UX target (§46): deploy → open app → create admin → enter site URL → connect WordPress → select LLM
  provider → start scan. Never require the user to configure ontology, entity schema, or agents up front.

## Domain vocabulary

The decision enum is closed (`README.md` §18) — proposals resolve to one of:
`KEEP | VERIFY | UPDATE | MERGE | PRUNE | NOINDEX | REDIRECT | RESTRUCTURE | LINK | CREATE | DO NOTHING`.
`CREATE` is deliberately *not* the success case; suppressing unnecessary generation is a first-class
outcome, and a failed Information Gain check yields `REJECT_NEW_CONTENT` (`README.md` §19).

Two graphs are kept separate and must not be merged: the **Knowledge Graph** (what we know about the world:
entities, facts, relationships) and the **Content Graph** (how that knowledge is placed on the web: pages,
passages, internal links, canonical/redirect relations) — `TechnicalArchitecture.md` §14.

Knowledge is hybrid: `Entity`/`Fact`/`Relationship` are structured; `Evidence`/`Observation`/`Question`/
`Problem`/`Experience`/`Claim` stay semi- or unstructured. Structure high-harm data first (prices, opening
hours, addresses, transit times).

Search visibility is not just Google rankings — organic search, AI search, search AI features, and video
search all count (`README.md` §24), with `citation_checks` / `visibility_checks` as later tables.

## Implementation ordering

`DatabaseSchema.md` §72–74 defines the build order. Phase 1 minimum tables are listed explicitly (sites,
sources, source_items, evidence, entities, entity_aliases, facts, claims, evidence_links,
knowledge_versions, content_items, content_versions, content_claims, queries, rankings, fact_staleness,
verification_requests, verification_events, opportunities, suppressions, plans, actions, action_results,
review_tasks, policies, site_policies, memories). Do not build Phase 1.5 or Later-Phase tables
(passages, serp_snapshots, campaigns, experiments, deployment_settings, …) unless asked.

Work is background-first, not realtime (`TechnicalArchitecture.md` §35): nightly knowledge refresh, daily
GSC import, weekly content decay analysis, hourly verification-response processing.

Model routing (§36): small model for classification/extraction, mid for entity resolution/summarization,
strong for planning, complex reasoning, and drafting.
